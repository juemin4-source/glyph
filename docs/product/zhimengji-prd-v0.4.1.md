### 0.4 名词解释

**本地项目**  
用户选择或创建的小说文件目录。项目中的真实文件构成作品事实源，同时限定 AI 的访问范围。

**创作现场**  
用户当前正在工作的状态，包括当前项目、当前文件、光标或选区、最近工作位置和正在进行的 AI 任务。

**AI 操作**  
用户交代一次任务后，AI 进行搜索、读取、生成、创建或修改所形成的完整行动记录。

**存档**  
AI 修改已有文件前保存的可恢复版本。

**来源标记**  
记录某段内容由 AI 写入，以及它后来是否经过用户编辑。

**增强能力**  
前提梳理、结构分析、设定整理、章节施工等原五画板能力。它们按需介入创作。

**正式提交**  
AI 生成结果经过校验与存档后，实际写入用户项目文件的动作。

### 0.5 核心决策记录

**D-001 本地文件为作品事实源**  
织梦机直接打开和编辑用户的真实本地项目。不再建立一份与本地文件并行的隐藏作品正文。

**D-002 自由创作是默认状态**  
用户进入项目后可以直接阅读、编辑和创建文件。即使 AI 不可用，写作工作仍然能够正常完成。

**D-003 AI 可以直接行动**  
在意图、范围和权限清楚的情况下，AI 可以直接创建或修改作品文件。用户无需在 AI 输出与编辑器之间复制粘贴。

**D-004 AI 行动必须留有记忆**  
每次正式修改需要：记录行动；保存必要存档；标记 AI 来源；支持查看结果；在安全条件满足时允许撤销。

**D-005 五画板改为增强能力**  
前提、结构、设定、章节施工和正文能力全部开放。用户按当前任务进入，不受开发时的冻结顺序约束。

**D-006 双入口、单工作区**  
织梦机提供两条首次路径：在织梦机开始创作；导入已有创作。两条路径最终进入同一个创作工作区和日常创作循环。

## 一、需求依据与阶段边界

### 1.1 产品概述

织梦机是一款面向长篇小说作者的本地 AI 创作工作台。

作者可以在真实本地项目中自由写作，也可以让 AI 搜索、读取、创建和修改作品文件；需要时还能调用前提、结构、设定和章节施工等创作方法。

系统通过存档、撤销、来源记录和权限边界，保障 AI 长期参与真实作品时的可控性。

### 1.2 目标用户

阶段一优先服务：已经进行真实小说创作、使用本地文件维护正文与资料，并尝试使用通用 AI 辅助写作的个人作者。

**典型特征：**
- 已经拥有实际作品或明确创作意图
- 使用 Markdown、Obsidian、Word 或文件夹管理正文
- 会将资料复制给 ChatGPT，或使用 Claude Code 等通用 Agent
- 重视自己的写作声音、目录结构和作品控制权
- 需要 AI 行动力，但不希望将作品交给全自动生成系统

**阶段一暂不面向：**
- 只希望一键生成整部小说的用户
- 多人编辑和出版社协作团队
- 以移动端碎片写作为主要场景的用户
- 需要复杂排版和正式出版输出的用户

### 1.3 两个核心场景

**场景 A：在织梦机开始创作**

用户尚未拥有完整项目，可能只有一个故事想法、一个人物、一段正文、一份零散设定或一个模糊的创作意图。

用户可以：直接创建空白正文；与 AI 展开想法；主动使用结构化创作引导。

成功结果是：用户获得第一份愿意保留、并知道如何继续的作品内容。

**场景 B：导入已有创作**

用户已经拥有正文、人物资料、大纲或施工卡，希望继续原来的作品。

织梦机需要：保持原目录结构；首次以只读方式观察；恢复最近创作现场；允许用户继续原来的写作；在用户授权后逐步提供 AI 行动力。

成功结果是：用户没有承受明显迁移成本，作品保持安全，并能立即继续创作。

### 1.4 核心问题

作者目前常将工作拆在多个环境中：本地编辑器中写作 → 查找和复制资料 → 交给通用 AI → 获得回答或文本 → 再复制回作品 → 人工判断是否覆盖和保留。

这一过程带来四类断裂：
1. **工作环境断裂** — 编辑、资料管理与 AI 行动分属不同工具
2. **项目上下文断裂** — AI 无法自然理解当前文件、项目结构和相关资料，作者需要反复补充上下文
3. **行动能力与安全机制断裂** — 普通聊天 AI 只能提供文本；通用 Agent 可以修改文件，却缺少面向作者的来源、存档和创作边界
4. **创作方法与自由写作断裂** — 结构化写作工具容易将方法变成强制流程；自由编辑器又缺少可按需调用的创作方法

### 1.5 用户故事

| ID | 故事 |
|----|------|
| US-001 | 作为一名已有长篇项目的作者，我希望直接打开现有目录并继续写作，以便在不迁移、不重组作品的情况下获得 AI 协助 |
| US-002 | 作为一名准备开始新小说的作者，我希望能够直接写，也能让 AI 或创作方法帮助我展开想法，以便迅速获得可以继续创作的内容 |
| US-003 | 作为一名作者，我希望 AI 能够自己搜索和读取项目中的相关文件，以便减少复制资料和重复说明 |
| US-004 | 作为一名作者，我希望 AI 可以直接创建或修改正文，以便让协作结果立即进入作品 |
| US-005 | 作为一名作者，我希望 AI 修改前有存档，修改后能看出来源和变化，以便放心让 AI 参与长期创作 |
| US-006 | 作为一名作者，我希望在遇到结构、设定或章节问题时调用专业方法，同时随时返回正文，以便获得方法帮助又不被流程束缚 |

### 1.6 产品北极星

成为作者长期使用的本地 AI 小说创作工作台。作者可以自由写作或让 AI 直接操作作品，也能在需要时调用结构化创作能力；所有内容归于同一项目，AI 行动可靠可逆，人机创作来源清晰可辨。

### 1.7 当前阶段目标

阶段一只建立自由创作底座：

打开或创建真实本地项目 → 稳定编辑 Markdown → AI 搜索和读取项目资料 → AI 创建或修改一个文件 → 修改前自动留存 → AI 内容来源可辨 → 用户能够撤销并继续创作

当前阶段暂不证明完整五画板价值。它首先验证：作者是否愿意把真实项目放进织梦机，并允许 AI 直接参与作品。

### 1.8 阶段假设

当以下能力同时成立时：写作编辑体验足够可靠；AI 能理解当前项目并直接行动；文件不会因 AI 失败而损坏；AI 内容来源清楚；修改可以恢复——作者会减少在编辑器和通用 AI 之间的切换与复制，并愿意在织梦机中完成连续的真实创作会话。

### 1.9 产品机制

| 机制 | 说明 |
|------|------|
| 自由创作常驻 | 用户随时可以直接阅读、写作和修改文件 |
| AI 在作品中直接行动 | AI 能在权限范围内查找、读取、创建和修改 |
| 结构化方法按需介入 | 方法由用户主动调用，或由 AI 根据任务建议使用 |
| 所有结果归于同一作品 | 正文、施工卡、分析和设定都回到用户的本地项目 |
| 行动安全可追踪 | 正式修改受到存档、来源、权限、记录和恢复机制保护 |

### 1.10 阶段范围

**In Scope：**
- 新建本地小说项目
- 打开已有本地项目
- Markdown 文件浏览与编辑
- 项目内文件搜索和读取
- AI 新建一个 Markdown 文件
- AI 修改当前文件或明确选区
- AI 修改前存档
- 最近 AI 操作撤销
- AI 写入来源显示
- 恢复最近创作现场

**Out of Scope：**
- 完整五画板重构
- 多文件批量修改
- 全项目自动重构
- Shell 和任意程序执行
- 项目目录外访问
- 多人协作
- 云端同步
- 移动端
- 精确到字符级的人机贡献谱系
- 完整版本树与分支合并
- 知识边界检测完整版
- 自动维护完整人物状态和故事时间线

## 二、产品结构与整体方案

### 2.1 整体用户体验路径

织梦机采用：两条进入路径，一个统一创作现场，一套持续创作循环。

```
入口 A：在织梦机开始创作
创作意图 → 创建作品 → 直接写 / 与 AI 展开 / 结构化引导
→ 获得初始内容 → 当前创作现场 → 日常创作循环

入口 B：导入已有创作
选择作品 → 只读观察 → 确认边界 → 恢复现场 → 当前创作现场 → 日常创作循环
```

### 2.2 日常创作循环

```
恢复现场 → 自由阅读与写作 → 出现当前任务
→ 自己完成 / AI 直接协助 / 结构化增强
→ 内容进入作品 → 作者判断并继续修改
→ 安全保存与沉淀 → 下次恢复现场
```

一次 AI 输出完成不是体验终点。核心成功时刻是：作者借助 AI 或方法恢复了创作动势，并继续写了下去。

### 2.3 最小领域对象

| 对象 | 说明 |
|------|------|
| **项目 Project** | 用户的一部本地作品及其根目录 |
| **文件 File** | 项目中的真实 Markdown 文件 |
| **AI 操作 AI Operation** | 用户一次任务及 AI 的搜索、读取、生成和写入行动 |
| **存档 Snapshot** | AI 修改前保存的文件版本 |
| **来源标记 Source Mark** | AI 写入文本块与对应操作之间的附属记录 |

**关系：**

```
项目
└── 包含多个文件

AI 操作
├── 发生在一个项目中
├── 读取若干文件
├── 创建或修改一个目标文件
├── 必要时产生一个存档
└── 写入后产生来源标记
```

### 2.4 关键状态

**文件状态：** 已同步；有未保存修改；正在保存；保存失败；外部已修改；文件不存在。

**AI 操作状态：** 等待；查找；读取；生成；写入；完成；失败；取消；已撤销。

**存档状态：** 可恢复；已恢复；因后续修改无法直接恢复。

**来源状态：** AI 原始写入；AI 初稿、用户已编辑；来源位置失准。

### 2.5 信息架构

```
一级工作区
├── 左侧：本地项目
│   ├── 项目名称
│   ├── 文件搜索
│   ├── 真实文件树
│   ├── 新建、重命名、删除
│   └── 文件状态
├── 中间：当前正文
│   ├── Markdown 阅读和编辑
│   ├── 当前文件与保存状态
│   ├── 光标和选区
│   ├── 字数
│   ├── 纯净模式
│   └── 来源模式
└── 右侧：AI 工作区
    ├── 自然语言任务输入
    ├── 当前 AI 任务
    ├── 读取依据
    ├── 执行过程
    ├── 结果和后果
    ├── 查看修改与撤销
    └── 历史操作入口

次级区域
├── AI 设置
├── 权限设置
├── 操作历史
├── 增强能力入口
└── 版本与恢复
```

### 2.6 用户、AI、系统分工

| 角色 | 职责 |
|------|------|
| **用户** | 决定作品方向；表达当前任务；决定是否让 AI 介入；确定必要的影响范围；判断结果是否符合创作意图 |
| **AI** | 理解任务；查找和读取材料；判断直接行动或调用方法；生成、创建、修改和分析；说明依据与结果 |
| **系统** | 文件正确保存；权限限制；修改前存档；正式提交；来源记录；外部变化检测；失败恢复；创作现场延续 |

## 三、详细功能方案

### 3.1 创建新作品

#### 3.1.1 功能目的

让用户从一个作品名称或初始想法出发，建立真实本地项目，并尽快进入可持续创作状态。

#### 3.1.2 入口

启动页：
- 创建新作品
- 打开已有作品

工作区内：
- 文件 → 创建新作品

#### 3.1.3 输入信息

必填：
- 作品名称
- 保存位置

可选：
- 初始想法
- 启动方式

启动方式包括：
- 直接开始写
- 与 AI 展开想法
- 使用结构化引导

选择只影响首次进入，不形成永久项目模式。

#### 3.1.4 正常流程

```
用户选择"创建新作品"
→ 输入名称与保存位置
→ 系统检查目标路径
→ 创建项目目录
→ 建立项目配置
→ 根据启动方式创建初始文件
→ 打开统一创作工作区
```

**直接开始写：**
创建 `作品名/正文/未命名正文.md`，编辑器立即获得焦点。

**与 AI 展开想法：**
创建一个空项目，并在右栏开启首次创作任务。用户给出的想法保存在项目中的普通 Markdown 文件内，不能只存在于聊天记录。建议初始文件：`创作起点.md`。

**结构化引导：**
进入增强能力入口。用户随时可以退出引导并回到正文。

#### 3.1.5 状态变化

- Project：不存在 → 创建中 → 可用
- File：不存在 → 已创建 → 已打开
- Workspace：无项目 → 当前项目已激活

#### 3.1.6 文件变化

系统允许创建：项目根目录；项目配置区域；初始 Markdown；必要的内部元数据目录。

内部目录不得影响用户使用其他编辑器。

#### 3.1.7 异常处理

**目录已存在：** 提示"此位置已经存在同名文件夹"。提供：使用现有目录；更改作品名称；更改保存位置。

**没有写入权限：** 提示"无法在此位置创建作品。请选择其他位置，或检查文件夹权限"。不得留下不完整项目。

**创建中途失败：** 已创建的空目录可以清理。若已经写入用户初始内容，应保留并说明位置。

#### 3.1.8 验收

- 能在中文路径下建立项目
- 新建项目能被普通文件管理器和其他编辑器正常访问
- 创建失败后不会留下伪成功项目
- 用户进入工作区后可立即输入正文

### 3.2 打开已有作品

#### 3.2.1 功能目的

让用户在不迁移、不重组、不破坏原文件的情况下，将已有作品接入织梦机。

#### 3.2.2 阶段一支持范围

**支持：**
- 打开一个本地目录
- 读取目录中的 Markdown
- 保留任意已有文件夹结构
- 识别最近修改文件

**阶段一暂不支持：**
- 将 Word 自动转换为 Markdown
- 导入 Scrivener 工程
- 自动重命名章节
- 自动重组用户目录
- 将多个散落目录合并成项目

TXT、Word 等文件可以显示在文件树中，但不承诺完整编辑与 AI 解析能力。

#### 3.2.3 正常流程

```
用户选择目录
→ 系统验证路径
→ 只读扫描目录
→ 展示扫描结果
→ 用户确认接入
→ 创建织梦机项目配置
→ 恢复或推测创作现场
→ 进入工作区
```

#### 3.2.4 首次扫描规则

**允许：**
- 枚举文件
- 读取元信息
- 读取受支持文本
- 建立搜索索引
- 推测文件用途

**禁止：**
- 修改原文
- 自动移动文件
- 自动重命名
- 自动创建分类目录
- 将推测写回正文
- 刷新原文件修改时间

#### 3.2.5 扫描结果

展示：
- 找到多少 Markdown
- 找到多少其他文件
- 哪些文件暂不支持
- 最近修改的文件
- 项目目录不会被重新组织

不要求用户逐个确认 AI 推测的文件类型。

#### 3.2.6 权限选择

首次接入默认：可读取项目，正式写入需用户开启。

阶段一提供三档项目权限：

| 权限 | 能力 |
|------|------|
| **只读** | AI 可以搜索、读取和分析 |
| **可新建** | AI 可以读取，并在项目内创建不重名的新 Markdown |
| **可修改** | AI 可以读取、新建，并修改当前明确目标文件 |

权限可以随时调整。删除文件、覆盖重名文件、批量修改仍需单独确认。

#### 3.2.7 异常处理

- **目录不存在或已移动：** 提示重新定位目录
- **部分文件无读取权限：** 其他文件继续载入，并列出无法读取的文件
- **项目过大：** 先显示目录树，索引在后台逐步完成。未完成索引不能阻止用户编辑

#### 3.2.8 验收

- 首次打开前后，用户原文件内容和路径一致
- 只读权限下 AI 无法写入
- 无法识别的 Markdown 仍能作为普通文本打开
- 用户可以不使用任何 AI 功能直接继续写作

---

### 3.3 项目文件树

#### 3.3.1 功能目的

如实展示用户项目，让用户浏览、创建和管理作品文件。

#### 3.3.2 常驻内容

- 当前项目名称
- 文件搜索入口
- 真实文件夹与文件
- 当前打开文件标记
- 文件异常状态

#### 3.3.3 支持操作

- 展开和折叠目录
- 打开文件
- 新建 Markdown
- 新建文件夹
- 重命名
- 删除
- 刷新
- 在系统文件管理器中打开
- 复制相对路径
- 作为 AI 参考文件

#### 3.3.4 文件状态显示

仅在必要时显示：未保存；保存失败；外部已修改；文件已丢失；AI 正在修改。

普通已保存文件不增加多余徽标。

#### 3.3.5 重命名与删除

重命名与删除属于用户明确发起的文件操作。删除文件进入系统回收站或产品可恢复区，不能默认永久删除。AI 阶段一不能自行删除文件。

#### 3.3.6 外部变化

文件树需要监听：新建；删除；移动；重命名；内容变化。

若变化不涉及当前未保存文件，自动刷新。涉及当前编辑文件时进入冲突处理。

#### 3.3.7 验收

- 文件树与硬盘目录一致
- 外部新建文件能被发现
- 重命名后当前编辑标签同步更新
- 删除当前文件时，编辑缓存不会立即丢失

---

### 3.4 Markdown 编辑器

#### 3.4.1 功能目的

提供足以承担真实长篇写作的主工作面。

#### 3.4.2 阶段一能力

- 中文长文编辑
- Markdown 基础语法
- 多文件标签
- 撤销与重做
- 查找替换
- 字数统计
- 选区
- 光标定位
- 自动保存
- 来源模式
- 恢复最近位置

#### 3.4.3 保存规则

用户停止输入后短延迟自动保存。同时在以下时机强制尝试保存：切换文件；关闭标签；关闭项目；应用退出；AI 准备修改当前文件。

保存状态包括：已保存；正在保存；有未保存修改；保存失败；外部已修改。

#### 3.4.4 AI 修改与用户编辑冲突

AI 提交正式修改前，系统检查：
- 编辑器是否仍有未保存修改
- 硬盘文件是否被外部修改
- 当前内容是否仍与任务发起时一致

若用户在 AI 生成期间继续编辑同一作用范围：AI 不得直接覆盖；结果转为待处理提案；用户可以查看或另存。

用户编辑其他无关位置时，可由技术方案判断是否能安全合并。阶段一默认采用保守策略：存在无法可靠判断的同文件变化时不自动覆盖。

#### 3.4.5 外部冲突

发现外部修改时，提供：
- 重新加载硬盘版本
- 保留当前编辑内容并另存
- 查看差异
- 明确覆盖

自动保存暂停，直到冲突解决。

#### 3.4.6 验收

- 长文输入无明显卡顿
- 切换文件不丢内容
- 保存失败明确可见
- Obsidian 修改当前文件后，织梦机不会静默覆盖
- 应用重启后已成功保存的正文保持一致

---

### 3.5 创作现场恢复

#### 3.5.1 功能目的

让作者重新进入项目时，迅速回到上一次创作位置。

#### 3.5.2 阶段一恢复内容

- 最近项目
- 最近打开文件
- 打开的标签
- 当前文件
- 光标位置
- 滚动位置
- 左右栏展开状态
- 未结束 AI 任务的基本记录

#### 3.5.3 恢复规则

恢复数据属于辅助状态。恢复失败不能阻止项目打开。

若原文件已经移动或删除：保留其他标签；提示缺失文件；回到文件树或最近仍存在的文件。

#### 3.5.4 产品表现

启动后优先回到正文，不先展示复杂仪表盘。可以显示轻量提示：`已回到上次编辑的 正文/ch31.md`。

#### 3.5.5 验收

- 正常退出后重新打开，回到原文件和位置
- 恢复数据损坏时项目仍能正常打开
- 缺失文件不会导致整个项目加载失败

---

### 3.6 AI 任务输入

#### 3.6.1 功能目的

让用户以自然语言表达当前创作意图，并自动携带必要的工作现场。

#### 3.6.2 输入入口

- 右栏输入框
- 正文选区快捷入口
- 文件右键入口
- @文件
- 增强能力入口

#### 3.6.3 默认上下文

一次任务默认包含：当前项目；当前文件；当前选区；光标附近内容；用户显式引用的文件。

当前文件不等于完整自动上传。AI 只在完成任务确有需要时读取内容。

#### 3.6.4 任务作用目标

任务卡必须能够表达：当前目标；作用文件；作用范围；可用权限；指定参考资料。

简单任务不要求用户手工填写这些字段。

#### 3.6.5 追问规则

AI 只在缺少关键创作判断时追问。典型情况：
- "帮我改好这一章"但修改程度不明
- 两份人物资料互相冲突
- 用户要求覆盖已有文件
- 目标文件无法确定
- 用户要求的事实没有可靠依据

不得因为内部工具选择而询问用户。

#### 3.6.6 验收

- 选区任务自动知道目标范围
- @文件能加入上下文
- 用户无需复制当前正文
- 目标明确的简单任务不出现多余确认

---

### 3.7 AI 项目搜索与读取

#### 3.7.1 功能目的

让 AI 自主取得当前任务所需的作品信息。

#### 3.7.2 阶段一能力

- 列出目录
- 按名称查找文件
- 搜索 Markdown 内容
- 读取指定文件
- 读取多个参考文件
- 引用当前选区

#### 3.7.3 权限规则

- 只能访问当前项目根目录以内
- 路径必须标准化
- 软链接、相对路径和其他方式不能绕过项目边界
- 只读模式下不得调用写入工具

#### 3.7.4 过程展示

默认显示简化记录：

```
查找：ch32 施工卡
读取：施工卡/ch32_施工卡.md
读取：正文/ch31.md
读取：人物/布兰.md
```

详细日志可以展开。

不展示：内部思维过程；Prompt；Token；Skill 内部路径；路由细节。

#### 3.7.5 依据与推测

AI 应区分：
- 文件中明确存在的信息
- 根据多份材料作出的归纳
- 没有依据的有限推测

缺少资料时不得假装已经找到。

#### 3.7.6 异常处理

**文件未找到：** 说明搜索结果并建议：指定文件；换关键词；从正文中寻找；允许有限推测。

**文件过大或不可读：** 说明未能完整读取，不将其列为成功依据。

#### 3.7.7 验收

- 用户能查看实际读取清单
- AI 不能读取项目外文件
- 未找到内容时不会伪造文件来源
- 部分读取失败不影响其他文件

---

### 3.8 AI 新建文件

#### 3.8.1 功能目的

让 AI 将新正文、施工卡或资料直接写入项目。

#### 3.8.2 前置条件

- 项目允许 AI 新建
- 目标目录存在或允许创建
- 文件名合法
- 不覆盖已有文件
- 生成结果完整

#### 3.8.3 正常流程

```
理解任务
→ 查找和读取资料
→ 确定目标路径
→ 生成临时结果
→ 校验内容
→ 创建正式文件
→ 创建来源记录
→ 更新文件树
→ 打开新文件
```

#### 3.8.4 文件重名

若目标文件已存在：自动建议新版本文件名；或询问用户是否修改已有文件；不得静默覆盖。

例如：`ch32.md 已存在` → `建议创建：ch32_v2.md`

#### 3.8.5 取消

AI 生成期间取消：正式项目中不出现半成品；临时内容可以保留在任务记录中；用户可选择保存为草稿。

#### 3.8.6 撤销新建

若新文件创建后未发生其他修改，可以撤销创建。若用户或外部软件随后修改：不直接删除；提供保留文件、另存内容或查看差异。

#### 3.8.7 验收

- 生成失败不创建空文件
- 新建文件真实存在于本地
- 文件树立即刷新
- 新建文件中的 AI 内容具有来源记录
- 重名文件不会被覆盖

---

### 3.9 AI 修改选区

#### 3.9.1 功能目的

让用户以最低风险将明确范围交给 AI 改写。

#### 3.9.2 前置条件

- 存在有效选区
- 文件允许修改
- 文件不存在外部冲突
- 用户意图明确

#### 3.9.3 正常流程

```
记录任务发起时选区
→ 读取必要上下文
→ 生成修改结果
→ 检查原选区是否仍未变化
→ 创建存档
→ 替换选区
→ 创建来源记录
→ 将光标留在修改附近
```

#### 3.9.4 生成期间用户改变选区

任务作用范围以发起时内容为准。若原文已经被用户修改：不自动覆盖；将 AI 结果显示为提案；提供对比和插入选择。

#### 3.9.5 结果表现

完成后轻量提示：`已修改所选的 3 段，修改前版本已保存。`

操作：查看修改；撤销；继续调整。不要求额外点击"接受"。

#### 3.9.6 验收

- 选区外内容保持不变
- 用户在生成期间修改选区时不会被覆盖
- 修改前存在可验证存档
- 完成后来源状态正确

---

### 3.10 AI 续写与当前文件修改

#### 3.10.1 阶段一范围

支持：
- 在明确光标位置插入
- 在文件结尾续写
- 修改用户明确指出的段落
- 修改整个当前文件，但必须告知影响范围

#### 3.10.2 整文件修改

整文件修改属于较大行动。执行前简要告知：`将修改 正文/ch32.md 的完整内容，原版本会自动保存`。

如果用户指令对情节保留范围不清楚，必须追问。

#### 3.10.3 提交规则

AI 生成期间不逐字覆盖正式文件。正式提交发生在：输出完成；内容通过基本校验；目标版本未发生冲突；存档成功。

右栏可以流式显示生成进度。

#### 3.10.4 验收

- AI 中断时正式文件保持完整
- 整文件修改前用户能够看见作用范围
- 存档失败时不执行正式覆盖
- 写入成功后编辑器内容与硬盘一致

---

### 3.11 AI 任务过程与结果

#### 3.11.1 任务卡结构

一次 AI 任务包括：
- 用户要求
- AI 对目标的简要理解
- 读取依据
- 当前行动
- 结果
- 文件变化
- 恢复入口
- 后续对话

#### 3.11.2 任务状态表现

| 状态 | 说明 |
|------|------|
| 等待 | 任务已经创建，尚未开始执行 |
| 查找 / 读取 | 显示当前外部行动 |
| 生成 | 说明正在形成结果 |
| 写入 | 明确目标文件 |
| 完成 | 说明产生了什么变化 |
| 失败 | 说明失败步骤和作品当前状态 |
| 取消 | 说明正式文件是否发生变化 |

#### 3.11.3 结果文案原则

回答四件事：依据了什么；做了什么；哪些作品内容发生变化；用户可以怎样继续。

简单任务可以压缩。

#### 3.11.4 任务分组

围绕同一目标的后续调整可以保留在同一任务单元。用户开始新的创作目标时建立新任务。

#### 3.11.5 验收

用户查看任务记录后，能够知道：AI 读过什么；改过什么；是否成功；是否能撤销；原作品当前是否安全。

---

### 3.12 存档

#### 3.12.1 功能目的

在 AI 正式修改已有文件前，形成可靠恢复依据。

#### 3.12.2 创建时机

必须在正式写入以前完成：

```
生成完成
→ 校验目标文件
→ 创建存档
→ 验证存档有效
→ 提交正式修改
```

存档失败时终止写入。

#### 3.12.3 阶段一存档粒度

阶段一按完整文件保存。原因：逻辑清楚；恢复可靠；容易验收；小说文本单文件体积通常可接受。

差异补丁可在后续版本评估。

#### 3.12.4 存档内容

- 原文件内容
- 原文件路径
- 文件版本标识
- 创建时间
- 对应 AI 操作
- 文件编码和必要元信息

#### 3.12.5 保存位置

具体采用项目侧车目录或应用本地数据区，由技术方案决定。

产品要求：不污染正文；存档能与操作对应；删除内部元数据不能损坏原文；项目复制后是否携带历史，需要在技术方案中明确。

#### 3.12.6 验收

- 每次已有文件 AI 修改前都有存档
- 存档与操作一一对应
- 存档内容与修改前原文一致
- 存档写入失败时正式文件不变

---

### 3.13 撤销与恢复

#### 3.13.1 一键撤销条件

同时满足：
- 存档存在
- 目标文件存在
- 当前文件仍是本次 AI 操作后的版本
- 没有后续用户编辑
- 没有外部变化

#### 3.13.2 一键撤销流程

```
检查当前版本
→ 保存恢复前状态
→ 写回存档
→ 更新来源记录
→ 标记操作为已撤销
→ 刷新编辑器
```

恢复动作本身也应留有恢复依据，防止用户误撤销。

#### 3.13.3 存在后续修改

禁止直接整体覆盖。展示：AI 修改前版本；当前版本；差异；另存为旧版本；明确选择整体恢复。

阶段一不承诺复杂三方合并。

#### 3.13.4 撤销新建文件

未发生后续修改时可移入回收区。存在后续修改时默认保留。

#### 3.13.5 验收

- 一键撤销后内容准确恢复
- 用户后续写作不会被静默删除
- 恢复失败时当前文件保持不变
- 已撤销操作在历史中有清楚状态

---

### 3.14 来源显示

#### 3.14.1 产品目的

让作者持续知道哪些内容来自 AI，同时保持正常写作体验。

#### 3.14.2 阶段一规则

一次连续 AI 正式写入形成一个来源块。来源块记录：文件；文本范围或可重新定位信息；对应 AI 操作；创建时间；用户是否编辑过。

#### 3.14.3 显示状态

| 状态 | 表现 |
|------|------|
| 用户内容 | 不做突出 |
| AI 原始写入 | 来源模式中轻微标记 |
| AI 初稿，用户已编辑 | 用户改动与 AI 区间重叠后更新状态 |
| 来源可能失准 | 外部修改或复杂文本变化导致无法可靠定位 |

#### 3.14.4 纯净模式

隐藏来源视觉区别。不删除来源记录。

#### 3.14.5 产品要求

- 不在 Markdown 中插入可见标签
- 不影响其他编辑器打开
- 来源失效时正文优先
- 不宣称精确的人机贡献比例
- 不追踪每一个字符的完整历史

#### 3.14.6 验收

- AI 写入后能显示来源
- 用户修改后状态更新
- 纯净模式正文显示正常
- 来源数据缺失或损坏时正文仍可正常使用

---

### 3.15 操作历史

#### 3.15.1 功能目的

让用户追踪 AI 曾经对作品做过什么。

#### 3.15.2 每条记录包括

- 时间
- 用户指令
- 读取文件
- 目标文件
- 操作类型
- 成功、失败、取消或撤销
- 是否存在存档
- 是否可以恢复

#### 3.15.3 历史不等于聊天记录

默认按行动组织。普通闲聊可以折叠在对应任务中。

#### 3.15.4 阶段一范围

支持：查看最近任务；查看读取依据；查看文件变化；撤销可撤销操作。

暂不支持：复杂版本树；历史分支；跨项目统一分析。

---

### 3.16 AI 设置与权限

#### 3.16.1 模型设置

- Provider
- 模型
- API Key
- 网络与连接测试

#### 3.16.2 项目权限

| 权限 | 能力 |
|------|------|
| 只读 | AI 可搜索、读取、分析 |
| 可新建 | 可读取 + 创建不重名新 Markdown |
| 可修改 | 可读取、新建 + 修改当前明确目标文件 |

删除、覆盖和批量操作不通过项目级权限自动放行。

#### 3.16.3 当前任务权限缩小

用户可以为单次任务限定：只读；只使用指定文件；只修改当前选区；只创建新文件。

任务级限制优先于项目级权限。

#### 3.16.4 隐私提示

用户应能知道：哪些文件内容会发送给模型；当前使用云端模型还是本地模型；API 调用失败时哪些数据已发送。

## 四、AI 交互统一规则

### 4.1 行动等级

| 等级 | 适用场景 | 说明 |
|------|---------|------|
| **一级：直接执行** | 项目内搜索；授权文件读取；文本分析；新建不重名文件；修改明确选区；在明确位置续写 | 前提是范围清楚且操作可恢复 |
| **二级：告知后执行** | 修改完整当前文件；生成较长新章节；调用复杂增强方法；创建新的正式结构化材料 | 告知后开始，用户可以取消 |
| **三级：确认后执行** | 覆盖已有文件；删除内容或文件；修改多个正式文件；改变目录结构；访问未授权位置；恢复可能覆盖后续创作；创作方向存在关键歧义 | 必须用户确认 |

### 4.2 AI 输出类型

AI 必须区分：

| 类型 | 说明 |
|------|------|
| **分析** | 没有改变作品 |
| **提案** | 等待用户决定方向或影响范围 |
| **已行动** | 作品已经发生真实变化 |

产品文案必须与实际状态一致。

### 4.3 增强能力调用

AI 可以在后台使用方法帮助判断。

出现以下情况时要告诉用户：将进入多步过程；将创建新的正式材料；任务目标会改变；完成时间明显增加；需要用户作出阶段性创作决定。

增强流程完成后回到原创作现场。

## 五、系统级异常与恢复

| 异常 | 正式作品状态 | 产品处理 | 用户下一步 |
|------|------------|---------|-----------|
| AI 生成中断 | 不变 | 保留已有临时结果 | 重试、保存草稿、放弃 |
| AI 写入失败 | 原文件不变 | 明确说明写入未完成 | 重试、另存 |
| 存档失败 | 原文件不变 | 阻止正式修改 | 重试存档 |
| 自动保存失败 | 编辑缓存仍在 | 显示持续状态 | 重试、另存 |
| 外部修改 | 暂停覆盖 | 展示版本冲突 | 重载、比较、另存、覆盖 |
| 文件被删除 | 编辑缓存保留 | 提示原路径不存在 | 另存、关闭 |
| 项目被移动 | 项目暂不可用 | 请求重新定位 | 选择新路径 |
| 路径越权 | 无变化 | 拒绝行动并记录 | 修改任务范围 |
| 来源记录损坏 | 正文不受影响 | 来源模式降级 | 重建或忽略 |
| 撤销存在冲突 | 当前正文不变 | 禁止静默恢复 | 查看旧版或另存 |
| 应用崩溃 | 取决于最近保存 | 启动后进入恢复 | 恢复草稿或打开正式版 |

### 5.1 错误文案结构

每个错误至少说明：什么步骤失败；正式作品有没有变化；是否保留了临时结果；用户现在可以做什么。

**示例：**

> 正文已经生成，但写入 `正文/ch32.md` 时失败。原文件没有变化，生成内容已暂存。你可以重试写入或另存为新文件。

## 六、产品规则与技术契约

| 产品规则 | 技术契约 |
|---------|---------|
| 本地文件是事实源 | 编辑器和 AI 最终读写同一真实文件；内部数据不得成为独占正文来源 |
| AI 修改前可恢复 | 存档验证成功后才能进行正式提交 |
| 未完成结果不进入正式作品 | 模型输出与正式文件提交分离 |
| AI 一次只改一个正式文件 | 阶段一写入工具强制单目标 |
| 读取过程可检查 | 每次工具读取写入操作形成结构化记录 |
| 导入不改变原目录 | 首次接入阶段只允许读取与内部索引 |
| 来源不污染正文 | 来源信息与 Markdown 内容分离 |
| 外部修改不被覆盖 | 写入前检查文件版本或修改标识 |
| AI 不能越过项目边界 | 所有路径解析到规范路径后检查根目录包含关系 |
| 取消后正式文件不变 | 取消只终止临时生成，不触发提交 |
| 恢复不能删除后续创作 | 发现版本不一致时禁止自动整体恢复 |

## 七、非功能性需求

### 7.1 数据安全

- 文件正式提交具备原子性
- 中途中断不能留下半个正式文件
- 存档与 AI 操作保持关联
- 自动保存失败明确可见
- 崩溃后尽量保留未提交编辑缓存
- 元数据损坏不能影响正文读取

### 7.2 性能目标

阶段一基准项目：
- 500 个以内文件
- 300 个以内 Markdown
- 单文件 20 万字以内
- 项目文本总量 500 万字以内

目标：
- 打开项目后文件树首屏在 2 秒内可操作
- 后台索引不阻塞正文编辑
- 普通文件切换在 300ms 内出现内容
- 中文长文持续输入无明显掉帧
- 保存后状态在 1 秒内更新
- AI 写入完成后文件树与编辑器在 1 秒内同步

以上为产品目标，需技术探针验证并调整。

### 7.3 兼容性

**阶段一：** Windows 10/11；UTF-8；中文与空格路径；Markdown；与 Obsidian 等文件型编辑器共存。

**阶段一暂不承诺：** macOS；Linux；云盘冲突完整支持；Word 排版保真。

### 7.4 权限与隐私

- API Key 加密或使用系统安全存储
- 文件访问仅限用户授权目录
- 明确提示发送给云端模型的内容
- 日志不得记录完整 API Key
- 默认不上传整个项目
- 只发送完成当前任务所需内容

### 7.5 可访问性与写作体验

- 主要操作可使用键盘
- 编辑器支持中文输入法
- 右栏可收起
- 来源模式可关闭
- AI 执行不抢夺编辑器焦点
- 弹窗不得频繁打断写作

## 八、数据统计与验证记录

织梦机属于本地创作工具，数据采集应最小化。

### 8.1 必要产品事件

在用户同意数据统计的情况下记录：

| 事件 | 用途 |
|------|------|
| project_created | 新建路径完成率 |
| project_opened | 真实项目使用情况 |

| ai_task_started | AI 任务使用 |
| ai_task_completed | 任务成功率 |
| ai_task_cancelled | 取消原因 |
| ai_file_created | AI 新建文件 |
| ai_file_modified | AI 修改文件 |
| ai_change_undone | 用户撤销 |

- AI 修改撤销率

- 用户是否减少复制粘贴
- 用户是否愿意开启修改权限

## 九、完整验收标准

### 9.1 Gate A：本地写作底座

**必须通过：**
- 创建新项目
- 打开已有项目
- 文件树真实同步
- Markdown 编辑
- 自动保存
- 恢复创作现场
- 外部变化检测

**验收故事：**
用户打开真实项目，编辑正文，使用 Obsidian 修改另一个文件，织梦机正确刷新；关闭重启后回到原文件，内容无损。

### 9.2 Gate B：AI 只读项目

**必须通过：**
- 项目内搜索
- 多文件读取
- 当前文件和选区上下文
- @文件
- 读取依据展示
- 项目外访问拒绝

**验收故事：**
用户询问角色当前知道什么，AI 自行找到人物资料和相关章节，并列出实际依据；未找到的信息明确说明缺失。

### 9.3 Gate C：AI 正式行动

**必须通过：**
- 新建 Markdown
- 修改选区
- 续写
- 整文件修改告知
- 临时生成与正式提交分离
- 单次单文件限制
- 重名保护

**验收故事：**
用户要求按施工卡创建新章，AI 读取资料后创建文件并自动打开；中途断网时不出现残缺正式文件。

### 9.4 Gate D：长期控制

**必须通过：**
- 修改前存档
- 一键撤销
- 撤销冲突保护
- 来源显示
- 用户编辑后来源更新
- 操作历史
- 崩溃与写入失败恢复

**验收故事：**
用户让 AI 改写选区，继续手写其他内容，再尝试恢复旧版。系统发现后续变化，不静默覆盖，并允许查看旧版或另存。

### 9.5 最终端到端主链

```
打开真实项目
→ 恢复上次创作现场
→ 手工编辑正文
→ AI 搜索施工卡与相关资料
→ 用户检查读取依据
→ AI 创建下一章
→ 文件真实落地
→ 用户修改 AI 正文
→ 选择一段让 AI 重写
→ 自动存档
→ 正式提交
→ 来源模式显示
→ 用户立即撤销
→ 正文恢复
→ 关闭并重启
→ 项目、正文、历史和来源状态正确
```

### 9.6 发布阻断条件

出现以下任一情况不得进入阶段发布：
1. 丢失用户正式正文
2. AI 失败后破坏原文件
3. 未经授权访问项目外目录
4. 外部冲突被静默覆盖
5. 存档失败后仍提交修改
6. 任务显示完成但文件未实际变化
7. 撤销删除用户后续创作
8. 来源机制污染 Markdown
9. 不使用 AI 时无法正常写作

## 十、阶段一研发顺序

| 里程碑 | 核心能力 |
|--------|---------|
| **里程碑一：文件可信** | 项目；文件树；编辑器；保存；外部变化；现场恢复 |
| **里程碑二：AI 看得见作品** | 搜索；读取；任务记录；权限；依据展示 |
| **里程碑三：AI 能够行动** | 新建；修改；临时生成；原子提交；单文件限制 |
| **里程碑四：作者敢让 AI 行动** | 存档；撤销；来源；操作历史；故障恢复；真实项目验收 |
